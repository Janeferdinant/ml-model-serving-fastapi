Verified (idle-machine rerun 2026-10-17, AMD Ryzen 7 5800X (8 cores, 16 threads), 32 GB RAM, Windows 11 Pro, High performance power plan, AC power).

Measured on this machine with the settings below. This is not a claim about production capacity or about any other hardware.

## Settings

- Hardware: AMD Ryzen 7 5800X (8 cores, 16 threads), 32 GB RAM, Windows 11 Pro, High performance power plan, AC power (16 logical CPUs); Windows-10-10.0.26200-SP0
- Software: Python 3.11.9, scikit-learn 1.9.1
- Started (UTC): 2026-10-17T11:44:52Z
- Server: uvicorn --factory mlserving.app:create_app --no-access-log, 127.0.0.1
- App config: MLS_RATE_LIMIT_PER_MINUTE=0 (limiter off), auth off, request log off, JSON access log on (stdout discarded), MLS_PREDICT_THREADS=1 (default)
- Model: v2 (production)
- Client: aiohttp, 4 client processes on the same machine, keep-alive connections, closed loop (no think time)
- Payloads: 500 pre-serialised bodies drawn from N(mean, std) clipped to the training range, seed 0
- Each repetition runs 15.0 s after a 4.0 s warm-up; 5 repetitions per cell; batch size 32.

## Command

```
python loadtest/run_loadtest.py --workers 1 4 --reps 5 --hardware "AMD Ryzen 7 5800X (8 cores, 16 threads), 32 GB RAM, Windows 11 Pro, High performance power plan, AC power"
```

## Notes

Rerun of the 2026-10-15 load test with identical settings (same client concurrency, 15 s duration, 4 s warm-up, payloads, seed, model v2) except 5 repetitions per cell instead of 3. The earlier numbers (`2026-10-15-loadtest.md`) were measured while other jobs held the CPU at about 100%; they are kept unchanged. 4-worker cells show 30 s client timeouts (22 requests in total: 5 in single-row 16 connections, 6 in batch 16, 11 in batch 64), each in the one or two repetitions where throughput collapsed to about 215 requests/s (the median is unaffected); the cause was not diagnosed. No repetition was discarded.

## Caveats

- **Machine state.** Not idle by the 15% criterion. The 60 s pre-run checks (six checks over 30 minutes, 07:14 to 07:44 local time) gave mean total CPU of 26.9% to 33.9% (maximum 44.9%), almost all of it one process of the owner's, SanDisk Dashboard, using about 3 of the 16 logical CPUs, which was not stopped; no other job or agent was running. The earlier shared-CPU run (2026-10-15) was at about 100% background. System CPU during the repetitions was 93 to 100%, which includes the load test's own four client processes and the server. A network interruption of the session happened between 02:12 and 07:13, before any timed run started; nothing was cut off or discarded. Power plan: High performance (active, not changed); AC power, no battery. Idle-check log: `2026-10-17-loadtest-idle-check.txt`. Peak system CPU during the repetitions was 100%.
- Client and server run on the same machine and compete for CPU.
- The load is closed loop: each connection waits for its reply before sending the next request, so latency reflects saturation at that concurrency, not a fixed arrival rate.
- Windows event loop (no uvloop); numbers on Linux will differ.
- `Errors` counts requests that failed or returned a non-200 status; they are excluded from latency and throughput.
